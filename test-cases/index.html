AIC / Форма «Начать проект» / Валидно заполненная форма успешно отправляется при корректной captcha

Позитивный сценарий. Priority: High. Проверка базового happy path для формы: валидные данные, корректная captcha и успешная отправка заявки.

Type

Positive

Priority

High

Preconditions

  • Открыта страница с формой Начать проект
  • Пользователь использует актуальный десктопный браузер
  • Тестовые данные соответствуют клиентской валидации формы

Notes

  • Этот сценарий нужен как базовая позитивная проверка для всей формы.
  • Сейчас именно этот поток блокируется багом по captcha integration.

Steps

  1. Открыть страницу с формой «Начать проект»
  2. Заполнить обязательные поля валидными данными
  3. Убедиться, что captcha загружена и доступна для прохождения
  4. Пройти captcha-проверку
  5. Нажать кнопку отправки формы
  6. Проверить реакцию интерфейса и результат отправки

Expected Result

Форма принимает валидные данные, captcha проходит без технических ошибок, а заявка успешно отправляется с понятным пользовательским подтверждением.

AIC / Форма «Начать проект» / При ошибке captcha форма показывает понятное сообщение пользователю

Негативный сценарий. Priority: High. Проверка пользовательского фидбека, если captcha-проверка не может завершиться успешно.

Type

Negative

Priority

High

Preconditions

  • Открыта страница с формой Начать проект
  • Поля формы заполнены значениями, проходящими клиентскую валидацию
  • Есть возможность воспроизвести сбой captcha-проверки в тестовой среде

Notes

  • Сценарий напрямую покрывает UX-проблему при техническом сбое submit.
  • По текущим артефактам этот кейс ожидаемо связан с багом отсутствия ошибки для пользователя.

Steps

  1. Открыть страницу с формой «Начать проект»
  2. Заполнить форму валидными данными
  3. Воспроизвести сценарий, в котором captcha-проверка завершается ошибкой
  4. Нажать кнопку отправки формы
  5. Проверить реакцию интерфейса после неуспешной попытки submit

Expected Result

Если captcha-проверка не пройдена или завершается технической ошибкой, форма показывает понятное сообщение об ошибке, объясняет, что отправка не выполнена, и подсказывает следующий шаг пользователю.

AIC / Форма «Начать проект» / Submit не получает Invalid key и 403 на captcha-check

Негативный сценарий. Priority: High. Проверка технической стабильности captcha integration во время submit.

Type

Negative

Priority

High

Preconditions

  • Открыта страница с формой Начать проект
  • Доступны DevTools для проверки Console и Network
  • Введены данные, достаточные для normal submit

Monitoring

  • Console
  • Network
  • Поведение кнопки отправки и формы после submit

Steps

  1. Открыть страницу с формой «Начать проект»
  2. Заполнить форму валидными данными
  3. Открыть DevTools и перейти в Console и Network
  4. Нажать кнопку отправки формы
  5. Проверить логи Console и сетевые запросы, связанные с captcha
  6. Сравнить фактический результат с ожидаемым

Expected Result

Во время submit captcha-проверка проходит без ошибок `Invalid key`, запрос `captcha-check` не возвращает `403 Forbidden`, а форма не блокируется на техническом уровне.

AIC-TC-004•Практический проект: тестирование сайта AIC•AIC / Start project form / Recovery flow
AIC / Форма «Начать проект» / После технической ошибки submit данные сохраняются и доступна повторная попытка

Негативный сценарий. Priority: Medium. Проверка recovery flow после неуспешной попытки отправки формы.

Type

Negative

Priority

Medium

Preconditions

  • Открыта страница с формой Начать проект
  • Поля формы предварительно заполнены валидными значениями
  • Есть способ воспроизвести ошибку отправки

Notes

  • Этот кейс усиливает UX-часть вокруг дефектов submit и error handling.
  • Даже если submit падает, пользователь не должен терять введённые данные.

Steps

  1. Открыть страницу с формой «Начать проект»
  2. Заполнить обязательные поля валидными данными
  3. Воспроизвести техническую ошибку на этапе submit или captcha-check
  4. Нажать кнопку отправки формы
  5. Проверить, сохранились ли введённые значения
  6. Проверить, может ли пользователь повторить попытку отправки без повторного ввода всех данных

Expected Result

После технической ошибки введённые данные не теряются, форма остаётся в предсказуемом состоянии, а пользователь может повторить попытку отправки после исправления проблемы или повторного прохождения проверки.

AIC / Mobile hero / Весь control «узнать больше» кликабелен по полной визуальной области

Негативный сценарий. Priority: Medium. Проверка, что mobile hero control работает как единый интерактивный элемент по всей своей визуальной области.

Type

Negative

Priority

Medium

Preconditions

  • Открыта главная страница AIC
  • Используется mobile viewport или реальное мобильное устройство

Notes

  • Сценарий нужен для проверки consistency между визуальным видом control и его hit area.

Steps

  1. Открыть главную страницу AIC в mobile viewport или на мобильном устройстве
  2. Найти control «узнать больше» в hero-блоке
  3. Нажать по текстовой части элемента
  4. Повторить действие, нажимая по точке и линии рядом с текстом
  5. Сравнить результат всех вариантов взаимодействия

Expected Result

Если текст, точка и линия визуально образуют один control, нажатие по любой части элемента должно вызывать один и тот же переход или интеракцию.

AIC-TC-006•Практический проект: тестирование сайта AIC•AIC / Homepage / Mobile hero legal block
AIC / Mobile hero / Legal-блок на мобильной версии переносится аккуратно и остаётся читаемым

Негативный сценарий. Priority: Medium. Проверка адаптации legal-блока в mobile hero без визуально рваных переносов и потери иерархии.

Type

Negative

Priority

Medium

Preconditions

  • Открыта главная страница AIC
  • Используется mobile viewport или реальное мобильное устройство

Notes

  • Этот кейс основан на UI review observation и помогает показать внимание не только к bug-level дефектам, но и к качеству мобильной адаптации.

Steps

  1. Открыть главную страницу AIC в мобильной версии
  2. Найти legal-блок в hero-секции
  3. Проверить переносы строк и расстояния между legal-ссылками
  4. Сравнить визуальное восприятие блока с соседними элементами первого экрана
  5. Убедиться, что legal-блок читается как цельный и аккуратно оформленный элемент

Expected Result

Legal-блок в mobile hero остаётся читаемым, ссылки не выглядят визуально разорванными, а переносы строк и интервалы не ломают общий вид первого экрана.

AGIMA / Форма «Стать клиентом» / Поле Email принимает корректный email

Позитивный сценарий. Priority: High. Проверка корректного email при валидном заполнении формы.

Type

Positive

Priority

High

Preconditions

  • Открыта страница https://www.agima.ru/clients/
  • Пользователь находится в блоке Контактные данные

Steps

  1. Ввести в поле Email корректное значение, например test@example.com
  2. Заполнить остальные обязательные поля валидными данными
  3. Проверить состояние поля Email
  4. Нажать кнопку отправки формы

Expected Result

Поле Email не подсвечивается ошибкой, значение считается валидным, а форма может быть отправлена при корректном заполнении остальных обязательных полей.

AGIMA / Главная страница / Мобильная версия корректно отображает контент без предварительного scroll

Негативный сценарий. Priority: High. Проверка initial render мобильной главной без предварительного scroll.

Type

Negative

Priority

High

Preconditions

  • Открыта главная страница https://www.agima.ru/
  • Используется mobile viewport или реальное мобильное устройство

Steps

  1. Открыть главную страницу в мобильной версии
  2. Дождаться полной загрузки

Type

Negative

Priority

Medium

Preconditions
